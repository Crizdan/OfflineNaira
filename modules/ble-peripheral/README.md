# modules/ble-peripheral

Local Expo module providing the BLE **peripheral** role that
`react-native-ble-plx` doesn't cover on Android: advertising the Offline
Naira service and running a GATT server with `TX_OFFER` (write) and
`TX_ACK` (notify) characteristics.

**Design note:** all chunking/reassembly logic lives once, in JS
(`src/protocol/ble-protocol.ts`), shared by both the central and
peripheral roles inside `BleService.ts`. Native is a thin GATT relay: it
doesn't chunk or reassemble anything itself, it just moves already-framed
chunk JSON in and out of the radio. This avoids hand-syncing the same
framing logic in both Kotlin and TypeScript.

## Setting this up

This folder is the module's source files, not a runnable scaffold by
itself — Expo local modules need scaffolding generated by the CLI
(Gradle files, the package manifest, etc.):

```bash
npx create-expo-module@latest --local
```

When prompted:
- module name: `ble-peripheral`
- native module name: `BlePeripheral`
- platforms: **Android only**

That generates `modules/ble-peripheral/` with the real scaffold. Then:

1. Replace the generated `android/src/main/java/expo/modules/bleperipheral/BlePeripheralModule.kt`
   with the one in this folder.
2. Replace the generated `index.ts` with the one in this folder.
3. Replace/merge `expo-module.config.json` with the one in this folder —
   it needs `"android": { "modules": ["expo.modules.bleperipheral.BlePeripheralModule"] }`
   so autolinking finds the class.
4. `npx expo prebuild --clean && npx expo run:android` on a **real
   device** — GATT server + advertising cannot be tested in an emulator
   (no real Bluetooth radio).

## What's implemented vs. what still needs device testing

The Kotlin is a complete implementation, not a stub — `startAdvertising`,
`startGattServer`, `notifyCharacteristic`, `isAdvertisingSupported`, and
the GATT callback (parsing each incoming TX_OFFER chunk and emitting it
to JS) all have real logic. It has **not been compiled or run** — no
Android toolchain or physical device available here. Expect to debug:

- MTU timing: `BleService.connect` (central side) requests a 517-byte MTU
  right after connecting, but if a chunk gets written before that
  negotiation completes, it can be silently truncated by the Android BLE
  stack. Worth adding a short delay or an explicit "MTU negotiated"
  handshake before the first real write if you see corrupted chunks in
  testing.
- Multiple simultaneous centrals: only one `connectedDevice` is tracked.
  Fine for a two-phone demo; extend to a `Set<BluetoothDevice>` if you
  need more.
- OEM-specific advertising quirks (payload size limits, background
  restrictions) vary across Android skins — test on more than one device
  model before trusting this broadly.

## API surface (matches `modules/ble-peripheral/index.ts`)

- `startAdvertising()` / `stopAdvertising()`
- `startGattServer()` / `stopGattServer()`
- `notifyCharacteristic(characteristicName: 'TX_ACK', chunkJson: string)` —
  `chunkJson` is one `JSON.stringify`'d `FramedChunk` from
  `frameMessage()`; native sets it as the raw notification value verbatim.
- `isAdvertisingSupported(): Promise<boolean>`

## Events emitted to JS

- `onTxOfferReceived({ msgId, index, count, payloadB64 })` — one event per
  BLE chunk written to TX_OFFER, same shape as `FramedChunk` in
  `ble-protocol.ts`. `BleService.ts`'s `subscribeToOffers` feeds these into
  its own `MessageReassembler` and only calls your listener once a full
  message is reassembled.
- `onCentralConnected` / `onCentralDisconnected({ deviceAddress })`
- `onAdvertisingFailed({ errorCode })` — maps to Android's
  `AdvertiseCallback.ADVERTISE_FAILED_*` constants.
